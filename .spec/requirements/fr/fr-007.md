# Require explicit approval and idempotency for writes

**Optional confirmed writes release.** A write proposal yields an opaque pending action with a summary and an expiry. Use a separate validated request variant on the authenticated AI route to approve or reject the action. The host policy rechecks permissions and dispatches the exact stored operation through host-backed idempotency. The confirmation protocol can also cover selected reads. [Release plan](../../planning/releases/rel-003.md).

## Acceptance criteria

- Only the authorized owner can approve the unexpired action. Rejection, cancellation before dispatch, cross-tenant attempts, stale configuration, and denied permissions result in no write.
- Concurrent approval, replay, and process restart cannot cause a second mutation for the same action. A timeout after dispatch preserves the original operation key and a recoverable outcome state.
- A writable method must explicitly declare confirmation and accept the backend-generated key via `@AiOperationKey()`. That parameter is populated by the executor from the approved action.
- Enabling future write support requires durable action storage, audited state changes, and business-layer idempotency. See [deferred write approval and idempotency](../../technical/auth/auth-001.md#deferred-write-approval-and-idempotency).
