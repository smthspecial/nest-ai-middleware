# Use SQLite by default with an injectable bookkeeping store

## Context

Bookkeeping records AI run status, model usage, and tool outcomes. A single Nest app can persist those records to a local file. Hosts that already operate a database or deploy multiple replicas may want all runs in a shared store using their existing database access and lifecycle. The same run semantics apply whether the host uses SQL, documents, or a remote service. [Bookkeeping specification](../services/srv-001.md)

The store must preserve application isolation, idempotent retries, immutable events, atomic finalization, and expiry. The core already has a proposed four-method `AiBookkeepingStore` contract for these operations. [Run and event records](../database/tbl-001.md), [event identity](../database/tbl-002.md)

## Proposed decision

The current module accepts one host-initialized `database.adapter` for conversations and bookkeeping. The repository ships SQLite, PostgreSQL, and MongoDB adapter packages. SQLite is the local default choice. Other driver, retention, and namespace options below remain proposals. [Current configuration](../services/srv-001.md#implemented-storage-configuration)

1. Keep bookkeeping opt-in. When a host enables it with a file path and omits `driver`, select SQLite through Node 26’s built-in `node:sqlite`. Default retention to 30 days and allow the host to override it. `driver: 'memory'` selects the bounded, process-local store. [Node.js SQLite](https://nodejs.org/api/sqlite.html)
2. Use `AiBookkeepingStore` as the common extension point. `driver: 'custom'` accepts an initialized store instance. A host can pass it to `forRoot()` or inject it into `forRootAsync()`. The host owns its client lifecycle and backend setup. Its adapter handles expiry and storage operations using the existing SQL client, ORM repository, document collection, or service client. [Nest custom providers](https://docs.nestjs.com/fundamentals/custom-providers)
3. Ship SQLite as the reference persistent implementation. Use the same contract tests for SQLite and future adapters. Add a ready-made adapter or a shared helper when multiple consumers need the same implementation and the supported backend combinations can be tested.

## Alternatives considered

| Option | How a host integrates | Tradeoff |
| --- | --- | --- |
| Host-implemented `AiBookkeepingStore` | Implement four lifecycle methods with the existing client and supply the instance through Nest. | Supports any backend that can enforce the contract and keeps the core dependency surface small. The host owns adapter code and storage-specific setup. |
| Ready-made adapter per engine | Install an optional adapter package or entry point for a supported SQL or document database and pass the host's client to it. | Smallest integration effort for supported engines. Each adapter adds its own migration or index strategy, compatibility matrix, and integration tests. Can coexist with host-written adapters. |
| Shared SQL adapter with dialect implementations | Supply a SQL client and select a supported dialect. Share bookkeeping logic and delegate statements, migrations, and constraint handling to the dialect. | Useful when several SQL engines need first-party support. Upsert syntax, conflict handling, types, and transaction behavior still require engine-specific work and tests. [SQLite upsert](https://www.sqlite.org/lang_upsert.html), [MySQL duplicate-key updates](https://dev.mysql.com/doc/refman/8.4/en/insert-on-duplicate.html) |
| Adapter built on an ORM or query builder | Provide a data source for the chosen library and use its models or migrations. | Reuses a host's existing stack when it matches. The adapter is coupled to that library and still needs to verify retry, expiry, and conditional update behavior on each supported engine. |
| Shared document adapter with backend implementations | Supply a document client that implements conditional writes, document lookup, and expiry. Share run serialization and storage layout. | Can reduce duplication across similar document engines. Atomic update APIs, document limits, expiry lag, and event queries remain backend-specific. [MongoDB atomicity](https://www.mongodb.com/docs/manual/core/write-operations-atomicity/), [MongoDB TTL](https://www.mongodb.com/docs/manual/core/index-ttl/) |
| Common low-level record or key-value interface | Implement insert-if-absent, lookup, compare-and-set, and expiration over a database, key-value service, or object store. | Broad in theory. It adds another adapter layer and leaves indexing, atomicity across related records, and cleanup guarantees to each implementation. The four bookkeeping operations are a smaller public contract. |
| Remote bookkeeping service | Inject a store that calls a service owned by the host. The service enforces storage semantics for every client. | Useful when several apps already share such a service. Adds network latency, authentication, failure handling, and a service to operate. |
| Append-only file, event stream, or queue | Persist lifecycle messages and derive run state and reporting from a projection. | Fits existing event pipelines. A durable append acknowledges receipt, while the projection has its own lag and deduplication. Matching the store contract requires a design for atomic finalization, retained state, and replay. |

## Store contract

```ts
export interface AiBookkeepingStore {
  checkReady(signal: AbortSignal): Promise<void>;
  startRun(run: AiRunStart, signal: AbortSignal): Promise<void>;
  appendEvent(event: AiRunEvent, signal: AbortSignal): Promise<void>;
  finishRun(result: AiRunFinish, signal: AbortSignal): Promise<void>;
}
```

- `checkReady` checks backend connectivity and the expected schema or indexes at startup. The host prepares the selected backend before startup.
- Carry `applicationKey` in each write. `startRun` uses the server-generated run ID. `appendEvent` uses the run ID and its server-generated sequence. Within a namespace, a retry with the same identity and payload succeeds without another record. A different payload on that identity is a conflict.
- `finishRun` atomically transitions a running run to a terminal status. An exact retry succeeds, and a conflicting terminal result is rejected. The adapter uses native conditions or a transaction to enforce this under concurrent requests.
- Pass the operation’s abort signal and stay within the existing bookkeeping budget. Runtime store errors use the existing sanitized failure path. Keep scheduled retention and reporting on the host side of the contract. [Store failure behavior](../services/srv-001.md#store-contract-and-failure-behavior)

## SQL and document storage layouts

- **SQL tables.** Store runs and events in separate tables. Use unique run and event identities, a conditional status update, and an indexed expiry on runs with cascading event deletion. This is the reference SQLite layout and gives other SQL adapters a model to follow. [Bookkeeping tables](../database/tbl-001.md), [event constraints](../database/tbl-002.md)
- **One record per run.** Embed bounded events in a document or a SQL JSON field. With conditional single-record writes, an adapter can check the event identity and update the run atomically. Expiring the whole record also removes its events. Record size limits, contention on a single record, and event-level reporting inform whether to use this layout. [MongoDB atomicity](https://www.mongodb.com/docs/manual/core/write-operations-atomicity/)
- **Separate run and event collections.** Use compound unique keys and a conditional run update. Carry the expiry timestamp into both collections or purge them together. Each TTL index acts on its own collection. When expiry is asynchronous, the host’s reports can filter by expiry time while deletion catches up. [MongoDB TTL](https://www.mongodb.com/docs/manual/core/index-ttl/)

## Host integration

The proposed built-in configuration needs an application namespace and a SQLite file path. Its parent directory belongs on a persistent volume when runs must survive container replacement.

```ts
bookkeeping: {
  applicationKey: 'orders-api',
  filename: './data/ai-bookkeeping.sqlite',
}
```

For a custom backend, the host exports a Nest provider for its implementation. In this example `AppDatabaseModule`, `APP_DATABASE`, `AppDatabaseClient`, and `AppBookkeepingStore` belong to the host. `AppBookkeepingStore` implements the same interface whether its client is SQL or document-based.

```ts
const BOOKKEEPING_STORE = Symbol('BOOKKEEPING_STORE');

@Module({
  imports: [AppDatabaseModule],
  providers: [{
    provide: BOOKKEEPING_STORE,
    inject: [APP_DATABASE],
    useFactory: (client: AppDatabaseClient): AiBookkeepingStore =>
      new AppBookkeepingStore(client),
  }],
  exports: [BOOKKEEPING_STORE],
})
class AppBookkeepingModule {}

AiModule.forRootAsync({
  imports: [AppBookkeepingModule],
  inject: [BOOKKEEPING_STORE],
  useFactory: (store: AiBookkeepingStore) => ({
    model,
    services,
    authorization,
    bookkeeping: {
      driver: 'custom',
      applicationKey: 'orders-api',
      retentionDays: 30,
      store,
    },
  }),
});
```

An application that already has the store instance can pass the same `bookkeeping` object to `AiModule.forRoot()`. [Nest dynamic modules](https://docs.nestjs.com/fundamentals/dynamic-modules)

## Consequences and verification

- Use the default SQLite file for a single app instance. A shared SQL or document store is available through the custom provider when replicas need shared writes. Validate SQLite lock contention against the request budget and evaluate a worker if synchronous calls can block the request thread. [SQLite WAL concurrency](https://sqlite.org/wal.html)
- Verify restart durability, exact retries, conflicting duplicates, concurrent finalization, namespace isolation, expiry of both runs and events, and bounded failures. Use real database fixtures for claims about each adapter. [Release test plan](../test-plans/tp-002.md)
- A store change selects the destination for new runs. Moving retained history between providers is a separate data migration.
- Adopting this proposal would put SQLite in the first bookkeeping release and make additional database adapters optional. Align the requirement, release criteria, and existing adapter tasks when adopting it. [FR-009](../../requirements/fr/fr-009.md), [TASK-011](../../backlog/tasks/task-011.md), [TASK-016](../../backlog/tasks/task-016.md)
