# Bind tools to existing NestJS providers and request contexts

## Context

An allowlisted class can be missing from Nest, registered in more than one module, or implicitly request-scoped through its dependencies. The executor must invoke the specific decorated method on the provider instance owned by the application.

## Proposed decision

1. At application bootstrap, require an own `@AiService()` marker on every allowlisted class. Use `DiscoveryService` to match it by exact provider token and metatype. Require one existing class provider per entry. Reject missing markers or bindings, duplicate registrations, aliases, factory/value substitutions, direct transient tool providers, and any ambiguous ownership. Imports of the same provider module may share one underlying registration. [NestJS discovery service](https://docs.nestjs.com/fundamentals/discovery-service).
2. Scan only own instance methods on that class's prototype. Read own decorator metadata, accept only string-named methods, and reject unsupported signatures. Capture the approved callable, binding, and compiled validators server-side. At invocation, verify that the instance still exposes the approved callable and bind `this` to the resolved instance. Getters, symbols, static methods, inherited methods, and instance replacements are outside the first contract.
3. Bind the registration to its owning module's `ModuleRef` and resolve the class token using strict, owner-local lookup with the supplied `ContextId`. Use one private Nest integration layer for the link from the discovery wrapper to the owner. Reject a token that is also a controller or enhancer binding in that owner, and treat incompatible wrapper layouts as startup errors. [NestJS module reference](https://docs.nestjs.com/fundamentals/module-ref), [NestJS module implementation](https://github.com/nestjs/nest/blob/master/packages/core/injector/module.ts).
4. For programmatic use, the host supplies a Nest context ID already associated with the trusted request. For HTTP, the future controller runs in the Nest request context and retrieves the existing ID with `ContextIdFactory.getByRequest(request)`. Preserve the original `REQUEST` object and the same ID throughout one interaction. Singleton services retain their existing instance. Context-scoped dependency trees stay isolated between requests. [NestJS injection scopes](https://docs.nestjs.com/fundamentals/injection-scopes).

## Consequences

- Business modules own their service dependencies. A host imports them normally and lists classes in `services`. Imports used to inject `forRootAsync()` factory dependencies must expose the needed tokens to `AiModule`. [NestJS dynamic modules](https://docs.nestjs.com/fundamentals/dynamic-modules).
- Duplicate registrations fail at bootstrap with diagnostics naming the conflicting modules. Tests use real Nest container bindings, including a service whose scope is inherited from a dependency.
- Inside the business method, Nest DI and service-layer authorization apply. Controller parameter pipes, guards, and interceptors from an existing REST route do not run for direct service calls. AUTH-001 defines the required tool policy.
