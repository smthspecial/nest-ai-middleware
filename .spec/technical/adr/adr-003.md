# Expose run records and tool events to host services

## Context

The plugin owns the SQLite connection and stores runs in `ai_runs` and generation and tool attempts in `ai_run_events`. Host services need to check whether a run is in progress, inspect its recorded tool activity, and react when an approved tool completes. The plugin needs a stable API that it can preserve as the storage schema changes. [Bookkeeping specification](../services/srv-001.md)

## Proposed decision

The current implementation exports `AiRunReader.readRun(runId, verifiedCaller, after?)` for owner-scoped reads of accepted output and paged bookkeeping events. It also exports local tool subscriptions through `AiToolEvents`. The broader read queries and durable delivery options remain proposed.

Export two injectable Nest providers when SQLite persistence is enabled. `AiRunReader` queries committed bookkeeping records. `AiToolEvents` delivers local, asynchronous notifications about committed tool attempts. Both use the plugin's existing SQLite connection and expose typed metadata. Keep the connection, SQL, schema, and all writes inside the plugin. A host can wrap the reader in its own authenticated HTTP route if it needs to expose this information to a dashboard.

### Read gate

| Operation | Response |
| --- | --- |
| `getRun(runId)` | Run ID, session ID when present, persisted status, start and finish times, and a stable error code when present. |
| `listRuns({ sessionId?, status?, cursor?, limit? })` | Page of run summaries, ordered by start time and run ID. |
| `listRunEvents(runId, { afterSequence?, limit? })` | Page of generation calls and completed tool attempts, ordered by the per-run sequence. Includes outcome, duration, reported token counts, and known tool and invocation IDs where applicable. |

- Bind the reader to access granted by the host. For a user request, derive the scope from the verified subject and tenant, then check ownership through the session before returning rows. For background services, use a host-registered consumer identity with explicitly granted installation or tenant scope. Apply the scope to the query before pagination. An unknown run ID and an inaccessible run ID produce the same result. Runs without a session are visible only to explicitly authorized installation operators.
- Use a default page size of 25 and a maximum of 100. Bind cursors to the active filter and access scope. Translate database failures into a stable unavailable error. Expose run and event metadata only. Transcript reads continue through the conversation API.
- `running` is the persisted status. It can remain after an abrupt process exit. The reader can expose partial progress through committed events. The current schema records tool attempts after they complete.

### Tool notifications

Host services subscribe with a principal established by the application. Each subscription selects stable tool IDs and an outcome filter that defaults to `succeeded`. The default scopes delivery to the same subject and tenant. Hosts can authorize service principals through `canObserveToolEvent`, checked asynchronously before a handler receives the event. Require an explicit filter for other outcomes. Publish events for registered tool IDs that were exposed to the run. Unknown tool attempts remain available through authorized bookkeeping reads.

Use a typed `ai.tool.completed.v1` envelope with `eventId` equal to the invocation ID, plus `runId`, `sessionId`, `sequence`, `toolId`, `outcome`, `occurredAt`, `durationMs`, and an optional stable `errorCode`. A successful tool event means that execution and result screening completed. The run can still fail later. A consumer that needs a successful final answer must check the run's terminal status.

Publish only after the corresponding `ai_run_events` insert commits. If bookkeeping cannot record the attempt, skip the notification and use the existing sanitized failure signal. Dispatch outside the request's tool path with a bounded queue for each consumer. Report queue overflow and handler failures through the host logger when configured. A handler failure must leave chat delivery and other subscribers available. Unsubscribe on module shutdown.

```ts
const unsubscribe = toolEvents.subscribe(
  { caller: verifiedMetricsPrincipal, toolIds: ['retail.catalog.product-trend'] },
  async (event, signal) => { await metrics.recordToolUse(event.eventId, event.toolId, signal); },
);
```

The retail metrics service can increment its usage counter with the invocation ID as its idempotency key. The notification provides the bookkeeping metadata for that invocation. The event does not carry prompts, replies, tool arguments, results, or credentials.

## Delivery options

| Option | Use |
| --- | --- |
| Read gate and SQLite queries | Inspect authoritative history, check run status, and diagnose a known run. |
| In-process subscriptions | React quickly in the same Nest process. Delivery is best effort and has no automatic replay after restart. Suitable for metrics and cache refresh. |
| SQLite outbox | Add when a reaction must survive restart or reach another process. Write the event and outbox row in the same transaction. Use a monotonic outbox cursor, per-consumer acknowledgement, and retries. Consumers deduplicate by invocation ID because delivery is at least once. |

Start with the reader and in-process subscriptions. Keep the durable option in the same plugin database if required. Introduce an external broker only for a host that has a cross-process delivery requirement it cannot meet with the SQLite outbox.

## Verification

- Check that a host service can see a run while it is active and retrieve its terminal status and persisted event history.
- Verify owner, tenant, and service scope checks on single-run reads, filtered pages, and subscriptions. Verify that inaccessible and unknown IDs behave identically.
- Execute the retail product trend tool and check that a subscribed service receives its stable tool ID and invocation ID. The subscriber should be able to read the committed event immediately through the gate.
- Exercise a rejected attempt, rollback or failed write, subscriber exception, queue overflow, and shutdown. Confirm that a failed write produces no notification and that a slow subscriber leaves chat and other subscribers available.
