# AI bookkeeping and persistence configuration

## Implemented storage configuration

The host initializes one adapter and passes it as `database.adapter`. The adapter enables both conversation persistence and run bookkeeping. Omitting the adapter leaves chat stateless. The host owns database connections, shutdown, and data retention. The core owns session access, history loading, and run bookkeeping.

```ts
AiModule.forRootAsync({
  imports: [HostDatabaseModule],
  inject: [HOST_AI_DATABASE],
  useFactory: (adapter: AiDatabaseAdapter) => ({
    model,
    database: { adapter },
  }),
});
```

| Adapter    | Storage                                                  | When migrations run                 |
| ---------- | -------------------------------------------------------- | ----------------------------------- |
| SQLite     | Host-selected file or `:memory:`                         | When the adapter opens the database |
| PostgreSQL | `nest_ai_middleware` schema in the host database         | When the host awaits `initialize()` |
| MongoDB    | `nest_ai_` prefixed collections in the selected database | When the host awaits `initialize()` |

Each adapter tracks its schema version. Version 1 adopts the storage layout and version 2 adds the conversation-owner index. The retail app uses SQLite by default. See the [adapter integration guide](../../../packages/core/README.md#adapter-packages).

## Conversation lifecycle

Session ownership requires the same verified subject and tenant for reads and follow-ups. `beginConversation` acquires a lease and creates a session for a new chat. An overlapping run receives `SESSION_BUSY`. `finishConversation` saves the accepted turn and releases the lease. Failed runs release their lease, and a new session with no saved turns can be discarded. Resuming a session loads all saved turns in order.

The SQLite adapter writes [session ownership and leases](../database/tbl-003.md) to `ai_chat_sessions` and [accepted exchanges](../database/tbl-004.md) to `ai_chat_turns`. The final assistant text stored in the turn matches the text returned by `sendMessage()`.

## Run records and visibility

The storage adapter implements `AiDatabaseAdapter`. Bookkeeping creates a run with `startRun`, associates it with the session using `attachRunSession`, records calls with `appendRunEvent`, and writes the terminal result with `finishRun`. Writes are best effort with a 100 ms budget per operation. The optional host logger can receive a sanitized bookkeeping failure.

SQLite writes [run status](../database/tbl-001.md) to `ai_runs` and [generation and tool events](../database/tbl-002.md) to `ai_run_events`. Events store timing, outcome, reported token counts, and tool or invocation identifiers where applicable. Accepted messages and final answers live in conversation turns.

If a prompt check rejects a run, Nest returns a generic HTTP 500. The run record can contain `SECURITY_REJECTED`, and middleware logs omit the rejection event. An input rejected before a session is acquired leaves a run with no session association.

Host services use `AiChatService.readRun(runId, verifiedCaller, after?)` to read run status, accepted output, and paged events after applying host authentication and authorization. Ownership is checked through the associated session. Keep the run record and its private rejection codes in the backend. [Run reader](../adr/adr-003.md)
