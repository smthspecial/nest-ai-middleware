# AI bookkeeping and persistence configuration

## Implemented storage configuration

The host initializes one adapter and passes it as `database.adapter`. SQLite uses a host-selected file. PostgreSQL uses a host pool and the `nest_ai_middleware` schema. MongoDB uses a host client and collections with the `nest_ai_` prefix. The adapters store only plugin sessions, turns, runs, and events. The host owns database connection lifecycle. The core owns session behavior, context selection, and run bookkeeping policy.

The retail example uses SQLite at `data/nest-ai-middleware.sqlite` in the workspace. Store session ownership and accepted exchanges in `ai_chat_sessions` and `ai_chat_turns`. Store run status and committed generation and tool events in `ai_runs` and `ai_run_events`.

Host services use `AiRunReader.readRun(runId, verifiedCaller, after?)` to retrieve the caller's run status, screened output, and paged events. The host applies its existing authentication and authorization first. `AiToolEvents` allows services to subscribe to committed tool attempt metadata by tool ID. See [ADR-003](../adr/adr-003.md).

## Draft design for additional database options

Phase 2 bookkeeping records authenticated interactions admitted by the controller, each model call's reported token usage, and bounded tool attempts. The host's normal guard logging covers requests denied before admission. Phase 4 adds opt-in user conversation history. The future write milestone adds a durable action store. These features have distinct retention and access rules. Executable tools come from the validated in-memory registry built from application code.

## Configure bookkeeping

| Configuration | Behavior |
| --- | --- |
| `bookkeeping` omitted | Collect no stored run records. |
| `{ driver: 'memory', applicationKey, retentionDays, maxRuns }` | Keep a process-local record with bounded capacity and expiry. Intended for examples, tests, and local inspection. |
| `{ driver: 'custom', applicationKey, retentionDays, store }` | Inject a host-selected persistent store. PostgreSQL is the first reference adapter. SQLite is an optional Phase 4 adapter. |

The following Phase 2 example uses the host's existing Nest providers. `HostBookkeepingModule` exports `AI_BOOKKEEPING_STORE`, backed by the optional PostgreSQL adapter and a host-managed connection pool. Connection strings, TLS settings, pooling, and credentials belong to the host database module. `applicationKey` is a stable, server-configured namespace for this installation.

```ts
AiModule.forRootAsync({
  endpoint: '/ai',
  authenticationGuards: [JwtAuthGuard],
  authorizationGuards: [AiAccessGuard],
  imports: [HostAiDependenciesModule, HostBookkeepingModule],
  inject: [AI_MODEL, AI_IDENTITY_RESOLVER, TOOL_POLICY, AI_BOOKKEEPING_STORE],
  useFactory: (
    model: AiModel,
    identityResolver: AiIdentityResolver,
    authorization: AiHttpAuthorizationPolicy,
    store: AiBookkeepingStore,
  ) => ({
    model,
    services: [OrdersService],
    identityResolver,
    authorization,
    bookkeeping: {
      driver: 'custom',
      store,
      applicationKey: 'orders-api',
      retentionDays: 30,
      writeTimeoutMs: 500,
    },
  }),
});
```

The host may also configure an identity projection that converts the trusted caller into bounded, opaque `tenantRef` and `subjectRef` values for reporting. The default stores neither reference. Configuration, retention, capacity, and timeouts must be validated before serving traffic. Both sync and async registration support an initialized store.

```ts
interface AiBookkeepingRetention {
  applicationKey: string;
  retentionDays: number;
  writeTimeoutMs?: number;
  projectIdentity?: (caller: AiCaller) => { tenantRef?: string; subjectRef?: string };
}

export type AiBookkeepingOptions = AiBookkeepingRetention & (
  | { driver: 'memory'; maxRuns: number }
  | { driver: 'custom'; store: AiBookkeepingStore }
);

export interface AiBookkeepingStore {
  checkReady(signal: AbortSignal): Promise<void>;
  startRun(run: AiRunStart, signal: AbortSignal): Promise<void>;
  appendEvent(event: AiRunEvent, signal: AbortSignal): Promise<void>;
  finishRun(result: AiRunFinish, signal: AbortSignal): Promise<void>;
}
```

`AiRunStart`, `AiRunEvent`, and `AiRunFinish` use the identifiers and bounded fields in the bookkeeping tables. Default the write timeout to 500 ms and reduce it when the interaction has less time remaining.

## Store contract and failure behavior

The bookkeeping adapter has four responsibilities. `checkReady` verifies the schema when the host enables a persistent adapter. `startRun` creates the run. `appendEvent` records one model call or tool attempt. `finishRun` transitions a running record to a terminal outcome. Each method receives an abort signal. The PostgreSQL adapter exposes a bounded `purgeExpired` operation for the host scheduler. A custom store documents how it applies expiry and capacity bounds in its own backend.

- Generate run UUIDs and per-run event sequence numbers server-side. Retry the same storage operation with the same identifiers when the host elects to retry. A repeated payload is idempotent. Reusing an identifier for different content is a store error. Finalization uses an atomic conditional update. A lost process can leave an incomplete run, which expires according to its retention deadline.
- Each model event records any reported input and output token counts separately. Missing usage remains unknown. Usage is informational and can be aggregated by run for operational reporting. Record only stable tool names, outcomes, durations, and bounded error codes. Omit prompt text, tool arguments and results, credentials, raw identifiers, and provider exception bodies.
- Use bounded writes within the request budget. A runtime store failure emits a sanitized operational signal and the read workflow continues. Retry failures at the storage layer only, with the original storage identifiers. Bookkeeping never triggers a second tool call or model generation. Writes requiring durable audit use the future action store contract and its stronger failure semantics.
- The memory store prunes expired runs, evicts the oldest completed runs when it reaches capacity, and reports dropped records when only active runs remain. PostgreSQL relies on the host's scheduled, bounded deletion of expired runs and cascading events.

## Database layout and deployment

| Migration | Tables | Release |
| --- | --- | --- |
| `001_bookkeeping` | [ai_runs](../database/tbl-001.md), [ai_run_events](../database/tbl-002.md) | Read-only release |
| `002_conversations` | [ai_conversations](../database/tbl-003.md), [ai_conversation_turns](../database/tbl-004.md) | Optional conversation history |
| `003_actions` | [ai_pending_actions](../database/tbl-005.md), [ai_action_events](../database/tbl-006.md) | Optional confirmed writes |

- Run the applicable versioned migrations with the host's deployment role. The application role receives the minimum table privileges needed by enabled stores. The library verifies schema compatibility at startup without running DDL. Exercise migrations from a blank schema and from each supported prior schema.
- Scope all reads, updates, and cleanup by application namespace. Conversation and action lookups also require the authenticated owner and tenant. Host reporting access is separate from the `/ai` API. Index ownership and expiry queries. Retention includes backups and replicas under the host's policy. [PostgreSQL constraints](https://www.postgresql.org/docs/current/ddl-constraints.html).
- Keep history disabled until the host supplies a store and retention. Only verified owners may load and append turns. Store bounded user text and validated public responses. Apply the host's content projection before retention. Append turns with an atomic expected-revision check. A conflicting request returns a conflict and can be retried explicitly. Expired or inaccessible history receives a uniformly safe response.
- The future action store requires atomic claims, durable state transitions, and a stable operation key. Persist the action and transition audit event in the same transaction. The business service implements its own atomic idempotency guarantee. Pending actions and conversation history use separate expiry rules. Store only data needed to approve, dispatch, or reconcile the action. [Write authorization and safety](../auth/auth-001.md#deferred-write-approval-and-idempotency).

## Later persistence options

Phase 4 adds `conversations` with an injected conversation store, `retentionDays`, and a bounded `maxContextTurns`. Configure optional content projection separately from bookkeeping identity projection. History reads, writes, and deletes use trusted application, owner, and tenant keys. Enable it independently of bookkeeping.

The optional write release adds `confirmations` with an injected durable action store, approval TTL, and resolved-action retention. A writable tool must declare `readOnly: false`, require confirmation, and explicitly accept an `@AiOperationKey()` parameter alongside its validated `@AiArgs()` parameter. The executor supplies the stored operation key. Keep the parameter out of the model-facing schema and let the host's business service use it for deduplication. Verify the corresponding host-backed idempotency integration before registering writable tools.
