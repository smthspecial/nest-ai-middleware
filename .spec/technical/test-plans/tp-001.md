# Phase 1 foundation integration test plan

Use Jest, `@nestjs/testing`, and an offline deterministic `AiModel`. Initialize fixtures through normal Nest bootstrap. Assert the identity of providers and request objects, and assert business-method call counts on every denied execution. Use controlled fake timers or deferred promises for timeout tests.

## Happy path

- Initialize through synchronous registration and an async factory that injects exported model and policy tokens. Preserve the supplied adapter and expose the executor through the public package entry point.
- Discover the example tool by its declared name and execute it with valid arguments. Verify the host service's original singleton, `this` binding, and dependencies.
- Combine and deduplicate class, inherited class, and method permission labels in either decorator order. Verify both sync module registration and an injected policy factory pass the full requirements and validated arguments to the host.
- Exercise explicit request scope and scope inherited through an injected dependency. Confirm the original `REQUEST` is available, two calls in one request reuse the correct instance, and simultaneous callers from different tenants get isolated results.
- Validate the adapter contract with a deterministic sequence containing multiple calls, results with matching IDs, a final reply, optional usage, and an abort signal. This fixture exercises the Phase 1 contract directly.
- Install a packed build in an independent host fixture. Check both runtime imports and TypeScript declarations on each supported Nest, Node, and module-format combination before declaring compatibility.

## Edge cases

- Fail bootstrap for duplicate tool names, a missing or ambiguous provider, a missing own `@AiService()` marker, a tool without effective permissions, empty or blank permission declarations, write or confirmation metadata, unsupported signatures, and invalid schemas. Verify a declaration shared through imports resolves to one provider registration.
- Fail safely for a provider token that collides with a controller or enhancer binding. Exercise singleton and request-scoped services owned by a module separate from `AiModule`.
- Confirm unsupported tool-calling capability can be declared by a Phase 1 adapter. Exercise typed tool errors, JSON serialization failures, output projection, and output-schema failure.
- Cover cancellation before dispatch, policy or DI resolving after the deadline, delayed tool completion after timeout, and sanitized failure propagation when the tool rejects.

## Abuse cases

- Reject calls to an undecorated method or a decorated method on a non-allowlisted class, including a class marked with `@AiService()`. Reject an unknown name, inherited method, or getter. A policy denial, policy exception, non-boolean policy response, or missing caller identity yields zero invocations. Confirm that method labels cannot replace class requirements.
- Reject extra fields, incorrect types, oversized values, cyclic or invalid JSON, and dangerous property keys before dispatch. A denied cross-tenant resource request yields no protected data.
- Verify model-facing tool definitions contain no server execution references. Verify sensitive output fields and raw service exceptions are stripped or rejected according to the host's projection and the core error policy.

Phase 2 adds HTTP and orchestration end-to-end tests. Pass host authentication and authorization guards through both registration methods. Verify that a DI-managed guard can read handler metadata, the authorization guard sees the principal set by authentication, and a denial yields zero controller, model, and service calls. Verify that global guards keep Nest's normal order, verified identity controls tool discovery, and the tool policy can deny a call after the HTTP guards grant route access. Phase 3 adds response-schema tests. A future write test plan must cover replay, expiry, concurrent approval, permission changes, and timeouts after dispatch.
