# Phase 1 foundation integration test plan

Use Jest, `@nestjs/testing`, and an offline deterministic `AiModel`. Initialize fixtures through normal Nest bootstrap. Assert the identity of providers and request objects, and assert business-method call counts on every denied execution. Use controlled fake timers or deferred promises for timeout tests.

## Happy path

- Initialize through synchronous registration and an async factory that injects exported model tokens. Preserve the supplied adapter and expose the executor through the public package entry point.
- Discover the example tool by its declared name and execute it with valid arguments. Verify the host service's original singleton, `this` binding, and dependencies.
- Verify automatic discovery of decorated tool methods on class providers. Check that inherited class and method guards run in the original Nest context.
- Exercise explicit request scope and scope inherited through an injected dependency. Confirm the original `REQUEST` is available, two calls in one request reuse the correct instance, and simultaneous callers from different tenants get isolated results.
- Validate the adapter contract with a deterministic sequence containing multiple calls, results with matching IDs, a final reply, optional usage, and an abort signal. This fixture exercises the Phase 1 contract directly.
- Install a packed build in an independent host fixture. Check both runtime imports and TypeScript declarations on each supported Nest, Node, and module-format combination before declaring compatibility.

## Edge cases

- Fail bootstrap for duplicate tool names, a missing or ambiguous provider, write declarations without opt-in, unsupported signatures, and invalid schemas. Verify a declaration shared through imports resolves to one provider registration.
- Fail safely for a provider token that collides with a controller or enhancer binding. Exercise singleton and request-scoped services owned by a module separate from `AiModule`.
- Confirm unsupported tool-calling capability can be declared by a Phase 1 adapter. Exercise typed tool errors, JSON serialization failures, output projection, and output-schema failure.
- Cover cancellation before dispatch, a guard or dependency resolving after the deadline, delayed tool completion after timeout, and sanitized failure propagation when the tool rejects.

## Abuse cases

- Reject calls to an undecorated method. Reject an unknown name, inherited method, or getter. A service guard denial, guard exception, or missing caller identity yields zero invocations. Confirm that class guards run before method guards.
- Reject extra fields, incorrect types, values outside schema constraints, cyclic or invalid JSON, and dangerous property keys before dispatch. Verify that large JSON arguments and results can pass when the tool accepts them. A denied cross-tenant resource request yields no protected data.
- Verify model-facing tool definitions contain no server execution references. Verify sensitive output fields and raw service exceptions are stripped or rejected according to the host's projection and the core error policy.

Phase 2 adds HTTP and orchestration end-to-end tests. Pass host authentication and authorization guards through both registration methods. Verify that a DI-managed guard can read handler metadata, the authorization guard sees the principal set by authentication, and a denial yields zero controller, model, and service calls. Verify that global guards keep Nest's normal order, verified identity controls tool discovery, and a service or method guard can deny a tool call after the HTTP guards grant route access. Phase 3 adds response-schema tests. A future write test plan must cover replay, expiry, concurrent approval, permission changes, and timeouts after dispatch.
