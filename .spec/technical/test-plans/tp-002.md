# Public release and production integration end-to-end test plan

Run the library through a real Nest HTTP application with a deterministic model and host guard fixtures. Use an independent packed consumer for each claimed runtime combination and real PostgreSQL or SQLite fixtures for adapter-specific guarantees.

## Current packed consumer coverage

The retail HTTP suite tests the installed core and SQLite packages. It covers guarded tool calls, owner-scoped conversations, SDK round trips, attachment screening, and generic HTTP 500 responses for security rejections. The core and SQLite suites also check independent input and output switches, persistence of private rejection codes, and suppression of those codes in the logger.

For the standalone compatibility check, install all four archives in a consumer using Node.js 24 and NestJS 11. Copy the fixture into that consumer and run it there to verify tool dispatch and SQLite persistence. Spolumi also exercises the packed core and PostgreSQL adapter with authenticated HTTP requests and a disposable database. [NestJS 11 check](../../../scripts/check-nest11.mjs).

## Planned release verification

- From `REL-001`, pass class-based Nest authentication and authorization guards, submit an authorized prompt, execute dependent read tools, and verify tool results round-trip to the offline model. Validate text and structured responses and exercise a request-scoped provider.
- Repeat the workflow with storage omitted and with each bundled adapter. Verify run, model usage, and tool records survive application restart when storage is enabled.
- From `REL-002`, resume an owner-scoped stored conversation after restarting the app. Exercise each supported SDK adapter, streamed and unstreamed output, semantic selection, and SQLite bookkeeping in the documented support matrix.
- From `REL-003`, propose a write, approve the immutable action using the same authenticated route, verify the stable operation key reaches the service, and reconcile a simulated crash without a duplicate mutation.

## Edge cases

- Expire deadlines during model generation, argument validation, provider resolution, service execution, and bookkeeping. Verify cancellation and stable errors. Test disconnects and streaming backpressure within the configured limits.
- Exercise invalid model batches, unexpected calls when no tools are offered, malformed response blocks, stale discovery cache entries, and missing token usage. Verify safe fallback and ordered call results.
- Retry persistence and migration operations where supported. Verify no duplicate book entries, compatible upgrades, bounded retention jobs, audit consistency, and recovery from an unavailable database.
- Race two conversation updates against one revision and two approvals against one pending action. Verify exactly one state transition wins each race and that a post-dispatch timeout preserves the original operation key.

## Abuse cases

- Deny unauthenticated and unauthorized route requests before model use. Attempt hidden and unregistered tool calls, forged principal and tenant fields, direct access by name, and prohibited arguments. Verify zero unauthorized service calls and zero sensitive disclosures.
- Inject tool result instructions asking the model to call hidden tools or ignore confirmation. Assert that all executor and authorization limits still hold.
- Attempt cross-tenant transcript access, action ownership changes, expired or replayed approval, permission revocation after proposal, and stale tool registration. Verify protected records and requests remain scoped to the verified caller.
- Inspect bookkeeping, logs, and telemetry exports for raw prompts, tool arguments, tool outputs, credentials, and identifiable references that were not explicitly projected by the host.
